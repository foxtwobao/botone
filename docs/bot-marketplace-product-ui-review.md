# Bot 市场产品方案与 UI/UX 评审

日期：2026-11-12  
评审对象：用户提供的「官方模板 MVP → 创作者发布 → 组织模板库」方案  
评审边界：只评审方案，不修改产品代码，不另行重做架构。

## 0. 评审依据与证据边界

本评审核对了调研文档，以及当前模板契约、安装服务、Web 弹窗、移动端列表与详情、应用连接卡和安装后初始化卡的静态代码。竞品结论来自 [bot-marketplace-research.md](./bot-marketplace-research.md)，不是本次重新实测竞品。

**本次没有实际 UI 原型或截图，也没有进行双端运行、真机、响应式、可访问性或视觉验收。** 下文涉及界面的内容均为基于现有结构的信息架构与交互建议；文中「当前已具备」仅指静态代码中可见的基础能力，不等于完整市场体验已经闭环。

## 1. 总体结论

### 1.1 结论：方向成立，但暂不宜直接进入完整高保真原型/视觉设计

方案的正确定位不是「从零做一个市场」，而是把现有模板发现与安装能力产品化：首期由官方控制模板质量和安全边界，复用现有副本安装、应用授权和初始化承接，再逐步开放创作者与组织能力。这条路径成本低、风险可控，应保留。

目前最主要的缺口不是卡片样式，而是**产品规则尚未唯一确定**：

1. 「一键安装」与「选择空间」「重复安装返回旧 Bot」「新版本安装」之间的语义没有统一。
2. 安装成功后，授权取消、失败、部分完成和 Routine 暂停分别如何继续，没有形成完整状态机。
3. 详情页没有明确区分「能做什么」「需要什么才能工作」「示例不等于实际结果」。

建议先补齐第 9 节的六项最小规则，再进入覆盖全链路的高保真原型。现在可以同步制作低保真 IA 草图，但不应把安装弹窗、授权结果和异常状态留给视觉设计临时决定。

### 1.2 定位、用户与 JTBD 建议

| 项目 | 评审建议 |
|---|---|
| 产品定位 | botone 内经过审核的 Bot 配置目录与分发入口；不是创作者社交平台，也不是插件、连接器或模型市场。 |
| 首期目标用户 | 已有 botone 账号、希望快速获得明确工作成果，但不愿从空白编写指令、技能和定时任务的个人用户或小团队成员。 |
| 次要用户 | 想验证 Bot 能否替代手工流程的新用户；创作者和组织管理员属于后续阶段，不应反客为主增加 MVP 复杂度。 |
| 核心 JTBD | 当我想完成一类重复工作时，我能快速判断哪个 Bot 适合我、它需要访问什么，并安装成自己的 Bot；即使暂不授权或启用自动化，也知道下一步能做什么。 |
| 成功标准 | 用户找到模板只是起点；应至少能正确理解能力与边界、创建独立副本、处理缺失连接，并完成一次手动使用或明确跳过初始化。 |

「Grok 的发现体验 + MausBot 的安全白名单 + botone 现有安装管道」适合作为内部策略概括，但不应成为验收替代品。验收要落到用户任务和异常路径，而不是三个名词。

## 2. 值得保留的设计

1. **官方模板先行，阶段边界克制。** 首期不做评分、付费、分成、评论、收藏、排行榜和完整公开网页市场，避免在内容供给与信任机制尚未验证前扩张。
2. **安装独立副本，不继承创作者身份、数据或权限。** 这是最容易被用户误解、也最需要坚持的信任基础；应贯穿详情、安装确认和首次使用，而非只写在安全说明中。
3. **白名单与权限最小化。** 当前 `BotTemplateSchema` 是严格结构，没有密钥、记忆、历史、模型和服务器字段；`templatePlan` 使用 `model:null`、`mcpServers:[]`、`apiKeys:[]`，Routine 均为 `active:false`。方案与现有安全边界一致。
4. **不自动授权、不自动覆盖已有 Bot。** 应用只是建议连接，更新不静默改写用户配置，均符合可预期性原则。
5. **复用预览版本预检、事务创建与幂等。** 当前已有 `BOT_TEMPLATE_CHANGED`、安装记录和归档 Bot 让位机制；重复请求有基础保护，无需为首期另造一套市场安装管线。
6. **安装后复用应用连接卡与初始化清单。** 当前未连接应用可生成连接卡，Routine 可进入 `Finish setting up` 清单；这比新增独立授权系统更符合最小实现原则。
7. **示例输出作为决策信息。** 示例能具体展示结果形态，是现有模板的优势；需要补充说明和降级预期，而不是删掉。
8. **Web 与移动端沿用各自导航形态。** Web 可在同一 Dialog 内列表/详情切换，移动端使用独立页面；不必强行统一为同一种容器，只需统一信息顺序、规则和状态。
9. **创作者发布与插件审核分层。** 可以复用限流、邮件确认、管理员审核能力，但 Bot 模板不与插件混为同种数据，避免权限和审核语义混淆。
10. **安装时快照。** 它为已安装 Bot 的独立性和后续「有新版」提示提供正确产品前提，但不能由此推导出 MVP 已有升级入口。

## 3. P0：进入高保真原型前必须明确

### P0-1：安装目标空间与重复安装语义冲突

**问题**  
方案同时承诺「选择空间」「一键安装」「独立副本」「重复安装幂等」「不覆盖已有 Bot」，但没有说明同一空间、不同空间、已归档、模板升级时分别执行什么动作。当前创建输入只有模板 ID、版本和名称，没有空间参数，安装使用当前 actor 空间；幂等键按模板 ID，不含版本，实际范围是**每用户、每空间、每模板**。已有未归档 Bot 时，当前双端按钮是 `Open`，会返回旧 Bot，而不是安装新版本或再建副本。

**用户影响**  
用户可能在错误空间安装，也可能以为「安装新版」实际只打开旧版；若按钮仍叫「安装」，又会误以为产生了第二个副本。这直接影响数据归属、信任和核心验收。

**具体修改建议**  
在方案中增加一张不可歧义的决策表，并作为双端原型共同规则：

| 场景 | 推荐 MVP 行为 | 主按钮/结果 |
|---|---|---|
| 当前空间未安装 | 安装到当前空间 | `安装` → 创建并进入该 Bot |
| 当前空间已安装 | 不新建、不更新 | `打开我的 Bot`；详情标注已安装 |
| 想装到另一空间 | 先显式切换目标空间，再按该空间状态判断 | 空间名始终出现在安装确认中 |
| 同一空间想再建一个副本 | MVP 不提供，避免与幂等规则冲突 | 不出现 `再安装一个` |
| 原 Bot 已归档 | 允许重新创建一个新 Bot，不恢复归档内容 | `重新安装`；说明旧归档不变 |
| 已安装后模板出新版本 | MVP 仅提示有新版，不自动更新 | `打开我的 Bot`；不提供误导性的 `更新` |

空间选择优先复用现有空间切换上下文，而非默认增加一个新选择步骤。若坚持在安装弹窗内选择空间，就必须同步定义接口输入、目标空间权限校验、空间切换后的已安装状态刷新，以及无可用空间/无权限的状态；这是新增产品与技术能力，不能写成「现有已支持」。

### P0-2：「安装成功」与「可以使用」之间缺少状态定义

**问题**  
方案把主链路写为安装 → 补充授权 → 开始使用，但没有定义哪些步骤阻塞首次使用。当前创建成功会直接进入 Bot 会话，未连接应用通过卡片引导，Routine 通过初始化清单开启；这不等于已有跨多个应用的统一授权向导或部分授权总进度。

**用户影响**  
Bot 已创建但无法产出示例结果时，用户会把降级、空结果或提示连接理解为安装失败；取消授权后可能失去入口，也不知道是否能先手动使用。

**具体修改建议**  
定义四个可观察状态，并统一双端结果承接：

1. **已创建，可手动使用**：无缺失必需连接，或用户选择暂不设置；直接进入会话并给出第一条推荐提问。
2. **已创建，待设置**：存在未连接应用或暂停 Routine；进入会话，保留应用连接卡和 `Finish setting up`，提供 `稍后设置`。
3. **已创建，部分设置**：至少一项失败、取消或仍待处理；明确列出已完成/未完成项，提供 `继续设置` 和 `先手动试用`。
4. **创建失败**：没有可用 Bot 时不显示成功；保留详情上下文和重试入口。若请求结果未知但 Bot 实际已创建，返回时依靠幂等打开同一 Bot，避免重复创建。

不要把「安装成功」等同于「所有能力已可用」。安装结果的主文案应区分 `Bot 已创建` 与 `完成设置后即可自动运行`。

### P0-3：所需应用没有必需/可选、不可用的产品规则

**问题**  
方案只写「所需应用」和「建议连接，不会自动授权」，没有区分核心功能依赖与增强项，也没有定义当前环境不支持某应用时怎么办。当前模板注释把应用描述为可缺失、Bot 仍可工作，但部分模板指令又明确要求某应用才能执行核心任务；`botTemplateApps` 只会返回目录中能匹配的应用，未匹配项会被省略，目录加载失败也没有独立提示。

**用户影响**  
用户无法在安装前判断授权是否必要；应用区消失会被误解为「不需要应用」，安装后才发现核心功能不可用。

**具体修改建议**  
- MVP 模板上架规则：每个声明应用标记为 `必需` 或 `可选`，并写一句用途；没有分类能力前，至少由模板内容审核明确，不允许把核心依赖写成泛泛的 `Works with`。
- 详情固定展示全部声明应用及状态：`已连接`、`待连接`、`当前环境不可用`、`状态暂时无法确认`；加载失败显示局部错误与重试，不隐藏整个区块。
- 必需应用未连接时，不阻止创建独立 Bot，但安装后必须给出对应连接卡，并显示「连接后才能执行 X」；可选应用未连接则说明哪些内容会省略。
- 当前环境不支持必需应用时，模板仍可供查看，但安装按钮禁用或改为 `当前环境不可用`，并解释原因；不要安装后才暴露。
- 若 MVP 不新增必需/可选字段，则应暂时只上架依赖语义一致的模板，并把结构化分类列为创作者发布前的必需前置，而不是靠文案长期兜底。

### P0-4：示例输出与安全说明可能形成过度承诺

**问题**  
示例展示邮件、日历、PR 等具体结果，但方案没有规定示例标识、数据条件和失败降级说明。安全说明又同时出现「建议连接」「不会自动授权」「独立副本」等抽象表述，没有转化为安装时的明确预期。

**用户影响**  
用户可能把示例当作自己真实数据、默认自动同步或安装后立即可得的结果；授权范围与副本边界虽有文字，却未在决策点被理解。

**具体修改建议**  
- 示例标题统一为 `示例输出`，紧邻标注：`演示数据，非你的真实内容；实际结果取决于你的输入、已连接应用和模型。`
- 对含草稿、发送、定时等动作的示例，补充模板级边界，例如 `只生成草稿，不会自动发送`；不要只用全局安全声明代替具体能力说明。
- 安装确认保留三行短文案：`创建一个独立 Bot`、`不会连接创作者的数据或账号`、`应用需由你自行授权，定时任务默认暂停`。
- 首次使用给出可立即执行的推荐提问；有缺失必需连接时，推荐提问不得假装能完成依赖该连接的任务。

### P0-5：版本变化、下架与旧预览的结果没有完整区分

**问题**  
当前已有版本预检和刷新提示，但方案中的「旧版本安装」「版本失效」尚未定义产品结果。移动端详情从列表缓存查找模板，找不到或加载失败会统一显示 `Could not load templates`，无法区分网络失败与模板下架。已安装 Bot 的快照与模板新版本之间也缺少展示规则。

**用户影响**  
用户看到通用错误时不知道是重试、重新查看还是永远不可用；已安装用户又可能误以为旧 Bot 已被改变。

**具体修改建议**  
- `模板已更新`：刷新详情，提示 `模板刚刚更新，请确认新内容后再安装`，旧预览不得直接创建。
- `模板已下架或不可用`：独立状态，返回目录；已安装 Bot 不受影响，并明确说明。
- `网络/服务失败`：保留旧内容时标注可能不是最新，提供重试；无内容时展示整页失败。
- MVP 只承诺安装时快照和「有新版」信息，不承诺覆盖升级、迁移、恢复旧版或安装第二份新版。

## 4. P1：核心体验完整性需要补齐

### P1-1：发现页的卡片信息优先级与搜索规则未定义

**问题**：方案卡片同时放名称、作者、简介、适用场景、所需应用、版本，15–20 个模板时容易过载；现有 Web 卡片已经包含较高的示例预览，继续叠加会稀释名称和用途。搜索也未说明匹配范围。  
**用户影响**：扫描成本升高，用户难以比较；搜索说明与实际结果不一致会降低信任。  
**具体修改建议**：卡片首层只保留图标/名称、一个官方或作者标识、单行结果导向简介、最多两个关键依赖或标签；适用场景与版本放详情，不在卡片展示完整示例。搜索 MVP 明确匹配名称、简介和作者，分类单独筛选；搜索框旁说明范围。作者只在小字次要层展示，官方标识优先于普通作者名。

### P1-2：空目录、无结果和局部加载失败没有状态设计

**问题**：现有双端对空数组没有专门空状态；应用目录失败时可能表现为应用区消失，详情未覆盖局部失败。  
**用户影响**：用户无法区分「没有内容」「筛选无结果」「网络失败」「没有所需应用」。  
**具体修改建议**：分别设计目录空状态、搜索无结果、分类无内容、整页加载失败、应用目录局部失败和详情不存在；无结果提供 `清除搜索/筛选`，空目录提供重试或返回，不使用模拟推荐填充。

### P1-3：详情页技术信息过早，用户语言不足

**问题**：当前双端以 `Adds` 聚合 Instructions、Skill、Routine，并展开指令与 prompt 全文；方案继续直接展示 Skills/Routines 术语，会使普通用户先理解系统概念，再理解收益。  
**用户影响**：详情变长，用户难以判断「它会做什么、何时运行、我能控制什么」。  
**具体修改建议**：首屏顺序统一为「能解决什么 → 示例 → 推荐提问 → 需要的应用与授权 → 自动化计划 → 安装」。将 Skills 展示为 `能力/工作方式`，Routines 展示为 `自动执行计划`；技术名称、完整指令和 prompt 放入 `查看配置详情` 渐进披露。保留原文供透明度审阅，但默认不展开。

### P1-4：Routine 默认暂停后的长期入口与启用反馈不完整

**问题**：方案只规定默认暂停，未说明用户稍后如何找回、启用前确认什么、启用后如何知道成功。当前 Web 有初始化清单入口，但静态证据不足以证明双端都拥有完整一致的市场安装后引导。  
**用户影响**：用户以为定时任务已运行，或找不到暂停任务；启用时忽略频率、时区和依赖。  
**具体修改建议**：安装后初始化清单列出每个暂停 Routine，显示人类可读频率和时区，按钮为 `去开启` 而非自动开启；跳转到既有 Routine 设置，返回后刷新完成状态。Bot 的 Routine 设置作为长期入口，不只依赖会话中一张历史卡片。启用失败保留在清单并允许重试；全部完成显示 `设置完成`，但应用授权和 Routine 分别计算，不混为一个成功。

### P1-5：授权等待、取消、失败、返回和部分成功没有逐状态文案

**问题**：现有应用连接卡有忙碌、超时、错误和已连接基础行为，但方案未定义多应用场景的总进度、返回路径与部分授权。  
**用户影响**：授权跳回后不知道是否成功；一个失败可能被误解为全部失败，或用户反复点击安装。  
**具体修改建议**：在首次会话的设置区逐项显示 `待连接/等待授权/已连接/连接失败/已取消`；失败文案说明仅该项未完成，提供 `重试`，取消提供 `稍后设置`。OAuth 返回原 Bot 会话，不重新安装；部分成功保留已完成状态。不要把 `稍后设置` 做成关闭后无法找回的临时弹窗。

### P1-6：安装中离开、返回和重复点击的行为需写进交互规则

**问题**：当前实现有防止离开后继续打开 Bot 的保护，但产品方案未描述安装中关闭弹窗、移动页面退出、网络超时后再次进入的结果。  
**用户影响**：用户可能重复安装，或认为取消弹窗就是取消创建。  
**具体修改建议**：明确 `关闭页面不等于撤销已提交创建`；安装中禁用重复提交，离开不自动跳转；再次进入同空间详情时刷新状态，已创建则显示 `打开我的 Bot`。请求失败但结果不确定时使用幂等重试，文案避免断言 `未创建`。

### P1-7：Web Dialog 与移动端需要同信息层级、不同呈现，不应只扩展现有容器

**问题**：Web 在单个 Dialog 内承载搜索、分类、卡片、长详情、安装状态和错误，可能出现长滚动与返回层级复杂；移动端若把所有字段和示例纵向堆叠，也会过长。  
**用户影响**：主 CTA 和授权信息不可见，返回路径不清，弹窗高度和移动端导航容易失控。  
**具体修改建议**：Web 列表与详情保持明确两级导航，详情顶部保留返回和主 CTA，长配置折叠；若高保真验证显示 Dialog 无法承载发现与详情，再改为页面，不以「必须继续用 Dialog」作为产品约束。移动端保持独立列表/详情页，主 CTA 可考虑底部固定，但不能遮挡错误和授权说明。两端均要求返回保留搜索、分类和滚动位置；实际断点、字体放大和键盘行为留待可运行原型验收。

### P1-8：15–20 个模板的内容生产与双端文案维护是 MVP 依赖，不只是核心数组扩充

**问题**：当前名称、简介和示例在 Web/mobile 分别按模板 ID 本地化，未命中回退服务器英文；模板详情与示例依赖人工内容质量。  
**用户影响**：扩量后容易出现双端文案、搜索命中和示例质量不一致，新增模板以英文回退，破坏市场完成度。  
**具体修改建议**：MVP 增加模板发布检查清单：分类、结果导向简介、示例及演示声明、推荐提问、依赖用途、暂停 Routine 说明、双端本地化、无密钥/私人数据、示例与实际能力一致。内容未齐的模板不上架；前端搜索只搜索用户实际可见的文案。

### P1-9：创作者与组织阶段有前置数据/规则，不应到二期再补来源语义

**问题**：后续阶段需要来源、作者、审核、下架和快照信息，但 MVP 若只考虑官方模板，容易把「官方」「作者」「已安装版本」做成不可扩展的展示假设。  
**用户影响**：未来用户无法判断 Bot 来自官方、创作者还是组织，也无法解释下架、更新和审核状态。  
**具体修改建议**：MVP 仅在数据与展示概念上预留 `来源类型`、`展示作者/发布者`、`模板版本`、`安装时版本/快照`；不把创作者投稿、公开主页、组织权限和自动更新塞进 MVP。二期前置包括导出白名单、脱敏/密钥扫描、投稿确认、驳回理由、修改后重审、下架对存量 Bot 的规则；三期前置包括空间发布权限、可见范围、撤下规则、组织审核责任。`availableInSpace` 可作为现有范围控制参考，但不能据此宣称组织模板库已具备。

## 5. P2：可在核心闭环后优化

| 编号 | 问题 → 用户影响 | 具体修改建议 |
|---|---|---|
| P2-1 | 六个分类与精选同时出现，15–20 个模板时部分分类可能只有 1–2 个 → 筛选显得空、精选占比过高。 | 精选控制在 3–4 个，默认先展示精选和全部；分类按实际内容量调整，允许一个模板有主分类，MVP 不做复杂多标签体系。 |
| P2-2 | 作者、版本、更新时间在首屏同等突出 → 决策信息噪声增加。 | 作者放名称下次要行，版本和更新时间放详情底部/安全信息区；只有版本变化或已安装新版提示时才提升优先级。 |
| P2-3 | 搜索无结果只给清空 → 用户不知道还能做什么。 | 后续可增加推荐相近分类或官方模板，但不得伪造模糊匹配；MVP 提供清除条件已足够。 |
| P2-4 | 卡片依赖名称和应用图标识别 → 模板增多后视觉同质化。 | 使用有限的分类图标/色彩体系，不为每个模板单独建立复杂插画资产；图标不是唯一状态表达，连接状态同时给文字。 |
| P2-5 | 安装完成后只进入空白会话 → 首次任务价值不够直接。 | 以推荐提问 chips、示例输入或预填输入框优化，但不得未经用户确认自动发送消息或启动 Routine。 |
| P2-6 | 官方精选规则只写 `featured` → 后续可能出现排序争议。 | 内容运营侧记录精选标准与轮换规则；MVP 无需公开算法、排行榜或个性化推荐。 |

## 6. 推荐的关键页面与状态清单

以下是最小原型覆盖范围，不要求为每个状态制作独立页面，可用同一页面的状态变体。

### 6.1 发现页（Web + 移动端）

- 默认：精选、分类、搜索、模板卡片。
- 首次加载、刷新中；整页加载失败与重试。
- 官方目录为空；分类为空；搜索无结果与清除筛选。
- 已安装模板在卡片上的轻量标识。
- 搜索、分类、返回后滚动位置保留。

### 6.2 模板详情

- 未安装：结果导向简介、示例及演示声明、推荐提问、应用需求、暂停 Routine、作者/版本/更新时间、安全说明、安装 CTA。
- 已安装：打开旧 Bot；有新版时只提示，不暗示自动更新。
- 应用：已连接、待连接、当前环境不可用、目录加载失败/重试。
- 模板：版本已变化并刷新、已下架/不存在、加载失败。
- 技术配置默认折叠，用户可查看指令、Skill 和 Routine 详情。

### 6.3 安装确认/空间选择

- 当前空间默认状态；多空间选择状态；空间无权限或无可用空间。
- 创建中、防重复提交、关闭/返回。
- 当前空间已安装、另一空间已安装、原 Bot 已归档后的重新安装。
- 创建失败、结果未知后的幂等重试。
- 版本预检失败返回更新后的详情。

### 6.4 安装后首次会话/设置承接

- 可直接手动使用；有待设置项；全部设置完成。
- 单应用等待授权、成功、取消、失败、超时、重试。
- 多应用部分完成；`继续设置` 与 `先手动试用` 均可用。
- 必需应用缺失时的能力降级说明；可选应用缺失时的内容省略说明。
- Routine 默认暂停、去开启、启用失败、启用成功、长期设置入口。
- 离开后返回原 Bot，不重复安装，授权状态刷新。

### 6.5 后续阶段原型（不进入 MVP）

- 创作者：投稿草稿、待邮件确认、审核中、驳回及理由、修改重提、上架、下架。
- 组织：空间私有目录、无发布权限、无可见模板、组织撤下、已安装快照说明。

## 7. MVP 范围建议

### 保留在 MVP

- 15–20 个经过审核的官方免费模板，分类、精选、前端搜索。
- 名称/简介/作者或官方标识的轻量卡片；详情含示例、推荐提问、依赖、自动化、版本与安全说明。
- 创建独立副本；当前空间或显式目标空间的唯一确定规则；幂等打开、归档后重装和版本预检。
- 模型继承现有用户/空间配置；模板不携带密钥、模型、记忆、历史、授权、MCP 或扩权配置。
- 应用由用户主动连接；Routine 默认暂停；复用现有应用连接卡与初始化清单承接设置。
- 双端加载、空状态、无结果、版本变化、授权取消/失败/部分完成、Routine 待开启等核心状态。
- 模板内容审核与双端文案检查，确保安全不变量和示例边界。

### 不扩大进 MVP

- 创作者投稿、公开创作者主页、评分评论、收藏、排行榜、付费与分成。
- 完整公开网页市场、Grok 链接导入、多注册表、digest 分发体系。
- 自动覆盖更新、模板迁移、安装多个同模板副本、组织模板库。
- 独立复杂授权向导、跨设备安装管理、个性化推荐。

**范围修正建议**：不要把「选择空间」默认为低成本 UI 项。若不能同步完成接口和权限上下文支持，MVP 应明确「安装到当前空间，并提供切换空间入口」，比做一个无后端支撑的假选择器更稳妥。同样，`有新版` 提示若不准备实现，就不应在 MVP 卡片或详情承诺更新入口。

## 8. 分阶段验收主线

1. **发现**：用户能按任务/分类找到模板，搜索无结果时可恢复；卡片能支持初步比较。
2. **理解决策**：进入详情后，用户能说出它做什么、示例不是实际数据、需要哪些应用、哪些任务会定时执行且默认暂停。
3. **安装**：目标空间明确，创建的是自己的 Bot；重复进入不会误建副本，也不会把旧 Bot 当成新版。
4. **授权**：未连接不会被自动授权；取消、失败和部分完成均可恢复，OAuth 返回不丢失上下文。
5. **首次使用**：即使暂不授权，也有可执行下一步；核心依赖缺失时不会给出虚假成功承诺。
6. **Routine**：安装后全部暂停，用户主动开启，能找到长期入口并确认频率、时区与启用结果。
7. **安全与版本**：恶意/非法字段不能绕过白名单；旧预览安装被拒绝；下架或更新不改写已安装快照。

## 9. 进入原型/视觉设计前的最小补齐清单

以下六项完成后，即可进入覆盖全链路的高保真原型；不需要等待创作者或组织方案完成。

- [ ] **一页安装规则表**：明确目标空间、同/跨空间重复安装、已归档、已安装新版、同空间第二副本的按钮和结果，消除「一键安装」歧义。
- [ ] **一页安装后状态机**：定义已创建、待设置、部分设置、创建失败，以及授权等待/取消/失败/成功、稍后设置和返回路径。
- [ ] **应用依赖规范**：每个模板标注必需/可选、用途、不可用和目录失败的表现；确定核心依赖缺失时的降级策略。
- [ ] **详情与示例文案框架**：固定信息顺序，增加演示数据声明、推荐提问、副本/授权/Routine 三条安全短文案；技术配置渐进披露。
- [ ] **双端状态矩阵**：覆盖第 6 节核心状态，并明确 Web Dialog 与移动页面的返回、刷新、滚动/筛选保留和长期 Routine 入口。
- [ ] **MVP 验收与内容门槛**：把第 8 节纳入验收；模板上架前完成分类、示例、依赖、本地化、安全和双端文案检查。

**最终建议：先规则、后高保真；先官方模板闭环、后创作者生态。** 上述六项属于定义现有方案的边界，不是扩大 MVP。补齐后，该方案可以进入原型/视觉设计；若仍以当前描述直接设计，最可能需要返工的不是视觉，而是安装按钮、空间选择、授权结果和版本状态。
