# 原生智能体执行架构精简方案

状态：目标架构已实现并完成离线、数据库、界面和 Docker 进程验证；真实付费模型轮次另作发布验收。直接采用目标架构，不保留宿主机执行服务的迁移兼容层。

## 目标与边界

保留内置运行时，并支持在用户选定的云电脑内运行 Codex、Claude Code、DSH。CLI 使用该电脑的文件、用户安装的软件、网络和持久化 home；用户只需选择电脑、智能体和模型。

部署者更新应用镜像和电脑镜像即可完成部署。取消这条默认路径对独立宿主机服务、systemd 安装、额外执行地址和令牌、专用反向代理的依赖。

优先在本功能已经新增的文件中调整实现。上游既有文件只保留必要、集中、显式的接入点；不以减少文件数为理由引入运行时打补丁、隐藏全局状态、重复配置解析或绕过权限检查。

首期仍只覆盖已经具备相应能力的 Docker 云电脑。其他电脑提供方通过能力检测明确降级，不为了接口统一而实现未经验证的启动路径。

## 决策：将现有原生执行模块接入 Supervisor

```text
API / Worker
  现有任务、授权、租约、消息与原生执行契约
        │ 已有电脑提供方连接和鉴权
        ▼
Supervisor
  新增的原生执行接入模块
  复用原生协议适配器和必要的执行状态管理
        │ Docker exec 双向流 + 可靠的进程停止机制
        ▼
用户选定的云电脑
  普通用户运行 CLI
  原生会话、用户依赖和工作文件保存在电脑 home
```

首版保留 `NativeExecutionProvider` 及 Worker 的调用方式。原生驱动和执行服务集中在轻量的 `@rakazo/native-runtime` 包，通过新增的组合模块接入 Supervisor，按需加载；Supervisor 的通用路由不包含厂商分支。该包只依赖中立适配契约和 Zod，Supervisor 不依赖整个后端适配器包。

暂不把驱动拆回 Worker。这样可以保留执行端的进程所有权、事件序号与接管语义，避免在迁移部署方式的同时重新设计跨进程双向协议。后续只有明确收益时再调整驱动运行位置。

### 生命周期分工

| 层 | 唯一负责的事项 |
| --- | --- |
| API / Worker 与数据库 | 用户和电脑授权、任务调度、租约与隔离代次、消息落库、任务最终状态 |
| Supervisor 内的原生执行模块 | CLI 进程句柄、协议收发、待处理交互、有限的事件重连缓冲、停止确认 |
| CLI | 推理与工具循环、原生会话和上下文、原生会话恢复 |

执行端仍需少量状态来处理重连、重复请求和停止确认，但不再维护另一套产品任务系统。复用现有 `service.ts` 中必要的状态与日志逻辑，确保 Worker 接管后不会重复执行。日志放在 Supervisor 私有数据目录，不能出现在电脑挂载目录中。

### 连接、授权与初始化

1. 从已有电脑提供方连接解析目标 Supervisor，兼容部署默认配置及数据库保存的提供方设置，不另建执行环境配置来源。
2. 新接入路由位于已有 `/computers/*` 鉴权和请求限制之下，复用电脑身份校验。后台仍须校验用户、空间、电脑归属；持有服务 Token 不等于可以跳过这些检查。
3. 不把 Supervisor 服务凭据复制到每个用户的执行连接记录，也不发送给浏览器、CLI 或电脑。记录只引用受控的电脑提供方连接；工厂在服务端解析当前凭据。
4. 复用现有个人模型授权、初始化 grant、启动前 Key 校验与恢复逻辑。部署服务凭据与用户模型 Key 始终分离。
5. 共享空间和个人空间继续使用现有授权边界。不得为简化部署自动给共享空间下发某个成员的个人 Key。
6. 模型配置继续走通用连接的协议默认值。模型目录有某个名称，不代表它支持所有协议；缺少对应协议配置时只影响该智能体。

## 进程执行：必须先证明的缺口

现有 `infra/sandboxes/supervisor/src/exec.ts` 提供实时输出和初始 stdin，但没有完整的持续双向协议接口。关闭 Docker exec 流也不能直接视作进程及其后代已退出。

新增专用进程传输模块，实现 `HarnessProcess` 所需的读行、写入、退出和停止能力。复用已有 Docker 客户端、容器身份解析和电脑生命周期，不改普通 shell 命令执行语义，不用 PTY 混合协议输出。

必要约束：

- CLI 以电脑普通用户运行，环境变量显式筛选；禁止继承 API、Worker、Supervisor 的数据库和部署凭据。
- stdout 作为协议流，stderr 独立处理；支持分片、多字节字符、背压和有界缓冲。
- 将平台工具桥接及权限代理的固定挂载路径改为本次运行可用的路径；不能直接照搬依赖宿主机 mount namespace 的旧路径。
- 停止先使用原生中断，再清理执行进程及其后代；确认完成后才结束任务。仅调用 `stream.destroy()`、发送一次信号或设置 AbortSignal 均不构成停止成功。
- 验证脱离进程组的后台子进程、忽略 TERM 的进程和退出期间继续产生子进程的情况。普通进程组方案不足时，先评估现有容器约束下可用的按运行进程隔离；不得因此默默开启 privileged、宿主机 PID 或扩大能力集。
- 一条任务停止不得终止桌面或其他任务。必要的电脑生命周期锁保持局部，不增加全局启动队列。

**停止机制是替换旧路径的前置条件。** 如果无法在现有容器权限下可靠实现，应记录失败证据并修订该设计，不能把风险转化为“用户手工清理”。

### 重连与故障

- 请求沿用 runId、scope、fence 和 generation；旧 Worker 的写入、审批回复不得作用于新执行。
- Worker 与 Supervisor 之间短暂断开，按原事件序号重连；租约过期后由执行端停止，不自动重新发送用户提示词。
- Supervisor 重启后，对无法确认的旧进程先清理或隔离；旧执行标记为丢失，不能自动重放。原生会话恢复只用于合法的新轮次。
- 云电脑替换后重新解析容器身份并核对 home 与归属，不能长期保存失效的容器 ID。
- 容器停止和升级继续经过既有电脑生命周期；新模块不能直接启动已停止电脑绕过网络恢复。

## 实施顺序与验收

### 第一步：验证最小进程链路

只增加进程传输、Supervisor 接入和对应测试。先用离线假进程验证双向流、分片、背压、进程清理与隔离，再用 Codex 验证多轮、审批、恢复、停止。新分支直接使用该通道，不保留旧部署路径。

通过标准：停止后后台写入确实结束，其他任务与桌面仍在；断线与重复请求没有重复执行；CLI 无法读取部署秘密；不需要新增宿主机服务或放宽电脑权限。

### 第二步：接入已有任务与授权

保留现有 `NativeExecutionProvider` 契约，把自动电脑连接解析到 Supervisor。覆盖启动、轮询、答复、停止等全部调用者。保留普通用户授权、撤销、共享空间限制和 Worker 接管测试。

### 第三步：迁移其余协议并切换部署默认值

复用进程通道迁移 Claude Code、DSH，按各协议执行真实验收。真实模型测试显式运行并单独记录费用；离线测试默认不需要外部账号。任一协议失败不得伪造就绪结果。

验证干净 Compose 部署、现有电脑更新及镜像回滚。web、Electron 和 mobile 复用现有能力契约，确认发现、选择、审批、停止正常；本次不添加新的配置页面。

### 第四步：移除旧基础设施

在同一分支删除不再使用的宿主机安装与镜像发布产物。清理方案造成的临时配置另作部署操作，不纳入公共仓库。

各步以独立、可评审的改动推进；不把尚未验证的复杂实现一次性合并。交付时附上上游文件数量和逐文件接入位置，说明实际与本方案估算的差异。

## 最终部署体验

1. 部署者使用包含原生执行接入的应用镜像和预装 CLI 的电脑镜像，沿用已有电脑提供方和模型连接设置。

默认路径不需要再安装宿主机执行服务、维护另一套服务地址和令牌，或为此增加代理配置。
